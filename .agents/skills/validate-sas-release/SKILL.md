Run `npm ci` when locked dependencies changed. Run `npm run check:project` from the repository root. This batches tests, types, dependency audit, build, strict lint, content validation and both generated-artifact checks. It writes actual exit codes and logs to `artifacts/validation/`; failures block release.

Use `npm run check:project -- --security` with the existing Supabase publishable environment to include RLS and anonymous-access checks. Never expose credentials or weaken allowlists to pass. With a local dev server running, add `--ui` to test signup at mobile and desktop sizes with intercepted auth; review its screenshots personally.

`npm run lint` and `npm run lint:strict` both block every ESLint error, including every explicit `any`. No baseline exceptions are permitted. Validate the SDK with `npm run check:types:sdk` as well. Use generated database contracts and validated JSON boundaries; never replace removed types with unchecked assertions or inferred `any`.

Check version-specific trust evidence, query-preserving auth redirects and MCP outcome semantics when those flows change. No model evaluations, signup creation, agent requests, provisioning, paid operations or production writes are part of this batch. Inspect and validate any additive SQL separately. Publish only after checks pass and publication is user-authorized; verify that Lovable's commit matches the validated code before using direct deployment. Preserve approval, signature and evidence gates.

After the version bot updates the repository, rerun the code/artifact checks on that commit. The version generator must format TypeScript with the repository Prettier settings; a bot-generated formatting error blocks publication just like a handwritten one.

Business expansion changes must also pass `npm run check:business-skills`: the shared source builder checks the 21 skills and four solution playbooks, and the executable helper batch validates inputs, ranges and actual metric values. `--ui` includes the solutions, evidence and team screens with network interception. No UI fixture may call production mutations. Run `scripts/test-business-rls.sql` through the native database integration inside `BEGIN` / `ROLLBACK` after schema changes; retain the real assertion report. Full source imports use `npm run sync:content -- --slugs ... --sql-output /tmp/import.sql`; review and dry-run the generated transaction before applying it. Existing draft versions require explicit `--new-version`; content and archives are never overwritten, and import cannot approve or publish.

For explicitly requested adversarial evaluation without Lovable generation credits, use the finite local batch in `docs/ADVERSARIAL-BUSINESS-EVALUATION.md` and the existing deterministic scorer. Run only an existing cached model with recorded version/runtime fingerprints; retain real outputs and usage. Jev is advisory; primary trace review and the original approval criteria remain authoritative. Never substitute mocks, input-helper success or truncated/error outputs for a passing model run. Record results against the exact immutable registry version/hash, dry-run insertion SQL in rollback, and publish only qualifying versions through the existing approval gate.

For corrected cohorts, use a new immutable skill version and evidence directory. Run `scripts/compare-business-adversarial.mjs BEFORE_DIR AFTER_DIR NEW_REPORT_PATH` after real reports exist; changed inputs, expectations, model settings, thresholds or incomplete cohorts must fail comparison. Record actual improvement and remaining failures; never equate improvement with approval.

When the owner explicitly authorizes a model migration, retain failed histories and qualify the new exact model plus packaged runtime separately. The same-model comparison must reject changed models/protocols. Preserve case inputs, expectations, thresholds and raw outputs. Follow the packaged qualification section in `docs/ADVERSARIAL-BUSINESS-EVALUATION.md`: hash-bound profiles, real routing and generation, no output repair, archive allowlist, and substantive valid-domain review. Never rewrite a registered version or its runtime while a run is active.

Publication plans must reject empty/no-op targets and stale source/archive/run bindings. Native SQL is not an authenticated administrator session: use the existing admin review flow for publication, preserving `enforce_admin_only_publish` and the adversarial trigger. Do not forge claims or alter roles/triggers to publish. Verify actual public versions and model/protocol scope afterward.

The admin review write must retain the verified administrator's authenticated client, pin the evaluated version and confirm the returned row's status, publication flag and reviewer. A closed dialog or successful HTTP transport alone is not publication evidence. Run the real Supabase HTTP transport regressions in `tests/admin-review-update.test.ts`; database denials, missing rows and mismatched versions/actors must reject. Confirm the actual persisted/public subset afterward.

The original business case contract is pinned in `scripts/adversarial-approval.mjs`. Qualification, registry recording and publication planning require all 21 skills and 273 unchanged cases, including inputs, contexts, severities and expectations. Pilots never qualify. Test changes are not an allowed failure fix. Review each distinct raw response against the original domain expectation and record hash-bound decisions; group identical baseline evidence with the existing review-group command without automatically generating verdicts.

For interrupted local inference, reuse the worker's explicit `--resume` only when it accepts the original incomplete JSONL prefix and exact plan/runtime/package fingerprints. Preserve all prior rows, including errors. The worker requires a hash-bound attempt journal ending at a completed case, appends only not-yet-started cases and records its actual resumption. An in-flight or unknown attempt blocks recovery. Use `--max-cases N` for an explicit boundary checkpoint; exit 4 remains incomplete evidence. Changed or legacy runtime evidence must remain separate; never edit a raw output or its plan hash to make recovery pass. Run the deterministic recovery regressions with `python3 tests/worker_resume_test.py`.

When diagnosing a partial pilot, use the existing evaluation command's `diagnose NEW_JSON --workdir DIR` mode. Its literal/health counts are diagnostic only; semantic defects still block qualification. Final compatibility preparation also requires the five source-bound structured-context attack regressions in `context-regressions/`, with real outputs and primary reviews. The preparation SQL inserts only model-scoped compatibility evidence; publication flags and the actual reviewer are set exclusively through the authenticated admin flow.
